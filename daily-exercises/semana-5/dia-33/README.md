# Dia 33: Kubernetes Networking - Services, CoreDNS Internal Discovery, and Kube-Proxy

## 1. Technical Overview and Objective

The objective of Day 33 is to dissect networking and service discovery in Kubernetes. Pods are ephemeral; when pods crash, scale, or get rescheduled, their IP addresses change unpredictably. Kubernetes Services solve this by providing a durable, static virtual IP (VIP) and DNS record that load-balances traffic across an elastic set of backing Pods selected via label selectors.

Key goals:
- Understand the Kubernetes Service abstractions: `ClusterIP`, `NodePort`, and `LoadBalancer`.
- Explore packet routing mechanisms managed by `kube-proxy` (iptables and IPVS modes).
- Master internal cluster DNS resolution via `CoreDNS` (`<service>.<namespace>.svc.cluster.local`).
- Inspect `Endpoints` and `EndpointSlices` controller synchronization.
- Configure and validate intra-cluster and external ingress traffic flows.

## 2. Architecture and Traffic Routing Breakdown

### 2.1 Service Types and Packet Routing Flow

```
+-------------------------------------------------------------------------+
| EXTERNAL CLIENT TRAFFIC                                                 |
+-------------------+---------------------------------+-------------------+
                    |                                 |
                    | (NodePort: Port 31000)          | (Cloud Load Balancer)
                    v                                 v
+-------------------------------------------------------------------------+
| WORKER NODE (IP: 192.168.1.50)                                          |
|                                                                         |
|  [Kube-Proxy (iptables / IPVS filter)]                                  |
|   - Maps VIP (10.96.0.100:80) to active Endpoint Pod IPs                |
|                                                                         |
|  +-------------------------------------------------------------------+  |
|  | CLUSTERIP VIRTUAL IP: 10.96.0.100:80                              |  |
|  | DNS: vote-service.development.svc.cluster.local                 |  |
|  +--------+------------------------+-----------------------+---------+  |
+-----------|------------------------|-----------------------|------------+
            |                        |                       |
            v                        v                       v
     [Pod 1: 10.244.1.15]     [Pod 2: 10.244.1.16]    [Pod 3: 10.244.2.8]
     TargetPort: 5000         TargetPort: 5000        TargetPort: 5000
```

### 2.2 CoreDNS Fully Qualified Domain Name (FQDN) Format

```
Format: <service-name>.<namespace>.svc.cluster.local
Example within same namespace:     curl http://vote-service:80
Example across namespaces:         curl http://vote-service.development.svc.cluster.local:80
```

## 3. Configuration Breakdown

### 3.1 Declarative ClusterIP and NodePort Service Manifest (`service.yaml`)

```yaml
# Internal Service for Redis caching
apiVersion: v1
kind: Service
metadata:
  name: redis-service
  namespace: development
  labels:
    app: redis
spec:
  type: ClusterIP
  ports:
    - port: 6379
      targetPort: 6379
      protocol: TCP
      name: redis
  selector:
    app: redis

---
# External-facing NodePort Service for Vote frontend
apiVersion: v1
kind: Service
metadata:
  name: vote-service
  namespace: development
  labels:
    app: vote
spec:
  type: NodePort
  ports:
    - port: 80
      targetPort: 5000
      nodePort: 31080
      protocol: TCP
      name: http
  selector:
    app: vote
```

## 5. Real-World Verification Methods

```bash
# 1. Inspect iptables rules generated by kube-proxy on the node
# Look for KUBE-SVC and KUBE-SEP chains
sudo iptables -t nat -L KUBE-SERVICES -n -v | head -n 20

# 2. Verify CoreDNS pods status and operational logs
kubectl get pods -n kube-system -l k8s-app=kube-dns
kubectl logs -n kube-system -l k8s-app=kube-dns --tail=20

# 3. Check for selector mismatches (Endpoints showing <none>)
kubectl describe svc vote-service -n development | grep Endpoints
```

## 6. Troubleshooting Takeaways and Lessons Learned

1. **Endpoints Showing `<none>` (Traffic Blackhole)**:
   - Cause: The label selector defined under `spec.selector` in the Service does not exactly match the labels under `spec.template.metadata.labels` in the Deployment.
   - Solution: Run `kubectl get pods --show-labels` and ensure exact case-sensitive key-value parity.

2. **`targetPort` vs `port` Confusion**:
   - `port`: The port on which the Service is exposed inside the cluster virtual IP.
   - `targetPort`: The port the actual container process is listening on inside the Pod.
   - If `targetPort` is configured incorrectly, connection attempts time out or return `Connection refused`.

3. **NodePort Range Constraints**:
   - By default, Kubernetes restricts `nodePort` allocations to the range `30000-32767`. Specifying a port outside this range returns an admission error unless modified via `--service-node-port-range` in `kube-apiserver`.
